# 3D 导演工作台：LibTV 调研与项目接入方案

调研日期：2026-10-04。使用 Edge 实际打开 LibTV 3D-BOX、官方预演工程和开源导演台；同时检查当前前后端、上游源码和供应商参数。本文是实现方案，3D 功能尚未接入 RuoYi Drama。

可以做。白模工作台的主要价值，是在生成正式画面前固定空间关系、人物运动、动作节奏和镜头路径。第一版宜复用开源编辑能力，增加项目存储、可靠导出和参考视频接入。完整复制 LibTV 的自然语言搭景与复杂表演质量，需要另外验证，不能从前端界面推断它的闭源实现。

## 当前项目能够复用什么

前端是 Vue 3 + Vue Flow，尚未安装 Three.js 或 Babylon.js。已有画布是节点关系编辑器，不能直接承担骨骼、机位和动画时间轴。可以复用项目选择、画布节点、素材引用、业务保存、模型选择、媒体任务恢复及合成流程。

关键现状来自当前代码：

- `src/utils/dramaCanvas.ts`：节点只包括文本、剧本、图片、视频、声音和分组；视频到视频的连线用于镜头顺序。
- `src/pages/short-drama/components/flow/useCanvasExecution.ts`：现有视频节点适配分镜、资产和声音绑定，适合作为后续接点。
- 后台 `ShortDramaCanvasService`：文档当前只接受 schema 1、固定节点种类，保存有项目归属及 revision 冲突检查。
- 后台 `VideoContext`：目前只有 `referenceImages`、`referenceAudios` 等，没有参考视频字段。
- 后台 `ShortDramaServiceImpl.generateVideoLocked`：提交参数及参数哈希未包含白模视频或其工程版本。
- 后台 `AtlasVideoGenerationServiceImpl.buildPayload`：没有发送 `reference_videos`。

因此，做出三维界面后还要扩展视频输入链路。白模不能作为普通“成片视频”节点混入镜头排序，否则会被误计入影片合成。

当前所用供应商已有对应能力：[Atlas Seedance 2.5 官方参数](https://www.atlascloud.ai/docs/more-models/bytedance/seedance-2.5-reference-to-video/generateVideo)公开 `reference_videos` 和 `@Video1` 引用；单条参考视频 2—30 秒、24—60fps，参考视频合计不超过 30 秒。参考生视频可显式选择 `omni_reference_task_type: reference`。白模视频、角色图片和场景图片可以分别承担运动、身份和画面参考。

供应商之间不能共用一套硬编码限制。例如 [fal Seedance 2.0](https://fal.ai/models/bytedance/seedance-2.0/reference-to-video/api) 使用 `video_urls`，最多 3 条、合计 2—15 秒；[Kling Motion Control](https://fal.ai/models/fal-ai/kling-video/v3/standard/motion-control/api)是人物动作迁移接口，有主体可见性等要求，不应默认等同于多人场景与完整运镜控制。以实际配置的供应商和模型能力决定允许提交的输入。

Seedance 官方介绍了 [白模控制与专业调度](https://seed.bytedance.com/en/seedance2_5)，说明这条路线具备模型支持；本次没有提交付费视频，未验证我们这套白模对生成结果的约束程度，不能承诺严格复现每个关节和每帧机位。

## 第一版怎么设计

入口在流程设计器空白右键及添加菜单中新增“3D 预演”，视频节点也能“打开 3D 导演台”。新节点显示工程缩略图、预演时长、工程版本、导出状态，并通过明确的参考关系连入视频节点。用户进入时可从空场景开始；模板作为主动选择。

编辑器使用 LibTV 的空间分配方式，并补足直接编辑能力：

- 顶部：工程名、预览功能标记、撤销/重做、保存、画幅及导出。
- 左侧：场景树和白模/道具库，添加、命名、隐藏、锁定、复制及分组。
- 中央：三维导演视口；机位小窗监看；俯视图方便画路线。
- 右侧：所选人物、物体或相机的属性；变换、姿势、动作、路线、镜头参数分别编辑。
- 底部：同一时间轴上的人物移动、骨骼动作、相机运动和镜头切换，拖动即可检查任意时刻。
- 导演助手：可收起；先读取工程与人工锁定，再提出结构化命令。应用命令进入同一撤销栈，不能生成任意 JavaScript 直接在页面执行。

第一版至少允许添加两个人物、墙、门框与基础道具；拖动摆位；行走、跑步、停下、转向及少量姿势编辑；分别编辑人物路线和相机路线；调整路线点、速度、停留和注视目标；构图监看、时间轴定位；保存恢复工程；导出干净白模视频并作为视频节点输入。

相机的移动轨迹和注视轨迹要分开：相机向右走时仍可看向左侧角色，不能用一根位置曲线同时代替朝向。人物的根节点移动与骨骼动作也要分开，走路周期要适配实际移动速度，避免脚滑。俯视图手绘路线先映射到地面，再成为可编辑轨迹点，另设高度、时长及注视对象。手绘完成后无需再次请求 AI 才能播放。

第一版的具体验收场景可以是：两个白模在门框两侧相遇，角色甲停下回头，乙继续靠近；摄影机从侧面跟随甲，再绕过墙角向甲推近。用户必须能独立修改甲的停留、乙的速度和相机的路线，再重新预演。这能检验空间遮挡、多人时序、注视目标和运镜的共同编辑能力。

### 技术接法

优先采用独立的 Three.js 编辑子应用，同源按需加载；宿主继续使用 Vue。复用 `3d-director-desk` 时保留其 React/R3F 编辑模块，增加我们自己的工程读写适配，不把外部 GitHub Pages 作为正式产品运行依赖。这样无需把成熟编辑模块全部重写成 Vue。

三维工程独立存储，内容包含 `projectId`、可选 `storyboardId`、`schemaVersion`、`revision`、稳定对象/相机/动作 ID、fps、人物轨迹、动作片段、相机关键帧、镜头段和素材引用。主画布只存三维工程编号和导出资产编号。扩展画布节点/参考边类型时提供旧文档迁移，并同步前后端校验，保证旧项目继续打开。

新增云端 load/save、项目所有权校验和 revision 冲突处理。自定义模型与动作上传到项目素材存储，保存哈希和持久 URL；不能跨设备保存 `blob:` 地址，也不能把 localStorage 当作正式项目数据库。人工锁定写在工程中，后端命令处理也须遵守。

导出按帧号求值，关闭编辑辅助线和标签，使用拍摄相机渲染。8 秒、24fps 的片段应生成 192 帧，逐帧求值区间为 `[0,192)`。编码后检查帧数、fps、尺寸、时长和完整解码；提供取消与任务恢复。先做 720p/24fps，1080p作为后续明确选项。

导出文件绑定工程 revision、内容哈希、镜头区间和相机 ID。工程修改后旧导出标记过期，生成不能静默沿用旧轨迹。模型提交增加参考视频及其哈希，并沿用当前视频任务的参数哈希、幂等、原任务恢复和导演稿审阅；不要新建一条绕过既有制作机制的生成入口。

用户选择“白模作为运动参考”时，提示词清楚区分 `@Video1` 的动作/走位/运镜与 `@ImageN` 的角色/场景外观。白模视频是空间与动作约束，不自动成为首帧，也不替换已批准图片或导演稿。首帧仍由用户显式选择，时长预算继续独立保存在 timing。

## 难度与范围

| 能力 | 难度判断 | 主要工作 |
| --- | --- | --- |
| 白模摆位、模型选择、三轴变换、场景树 | 中低 | 开源编辑模块已有，处理项目化和界面定制 |
| 人物路线、相机轨迹、注视目标、监看、时间轴 | 中 | 统一时间和坐标，保证修改/撤销/恢复结果一致 |
| 保存、导出、接到现有画布和视频模型 | 中高 | 工程存储、素材持久化、稳定帧率、模型能力及原任务恢复 |
| 走、跑、转身、抬手等基础表演 | 中 | 动作片段、速度匹配、转场与简单关节调整 |
| 拥抱、格斗、持物接触、摔倒、多人同步 | 高 | 动作素材、骨骼映射、混合、IK、脚部接地和接触约束 |
| 一句话自动搭景并生成复杂连续表演 | 高 | 规划、约束验证、受控命令、失败修复及质量评估 |

按一名熟悉三维的前端开发者配合一名后端开发者、复用开源模块估算，可编辑并打通保存与参考视频的第一版约 2—3 周；复杂动作、可靠的自然语言调度和较充分的验收另需约 4—8 周或更久。这是范围估算，模型遵循程度需要实际样片实验，不能按工期保证。

建议第一轮就交付可从零编辑的白模、人物路线、相机路线、共同时间轴和可靠导出；下一轮加入结构化导演助手，复杂接触动作另做素材与骨骼验证。
